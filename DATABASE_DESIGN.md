# QRBank Database Design Proposal

**Status:** Database Review Draft  
**Scope:** PostgreSQL schema design only  
**Implementation status:** No migrations, ORM models, or production code are authorized by this document.

---

# 1. Executive Summary

QRBank should use a normalized PostgreSQL schema with UUID primary keys, classroom-scoped human-readable codes, strict foreign keys, targeted composite foreign keys for tenant consistency, integer point balances, an append-oriented financial ledger, explicit idempotency records, and separate operational tables for behavior, jobs, rewards, inventory, fulfillment, automation, and administrative auditing.

The central financial design has two complementary sources of information:

- Enrollment.current_balance is the fast current balance used by the application.
- FinancialTransaction is the permanent financial audit trail.

Only the central financial transaction service may modify Enrollment.current_balance. Every successful balance change creates exactly one committed FinancialTransaction. Rejected business requests are recorded through FinancialRequest rather than by creating failed ledger rows.

The schema deliberately separates:

- User from ClassroomMembership
- Student from Enrollment
- Action from QuickAction
- financial ledger from BehaviorEvent
- Reward from RewardPurchase
- purchase finance from reward fulfillment
- current reward inventory from RewardInventoryEvent history
- automation run observability from per-payment idempotency
- financial audit history from administrative audit history

Generic QR commands are resolved using classroom-scoped codes:

    STUDENT:<StudentID>
    QUICK:<QuickActionID>
    ACTION:<ActionID>

No QR token table is required for V1.

The most important database-level tenant-safety pattern is to store classroom_id directly on classroom-owned records and use composite foreign keys where useful. For example, a transaction references Enrollment through both enrollment_id and classroom_id, making it impossible for the transaction to claim Classroom A while pointing at an enrollment from Classroom B.

# 2. Requirements and Approved Architecture Constraints

This design preserves the approved architecture:

- PostgreSQL is authoritative persistence.
- All point values use integer arithmetic.
- Student and Enrollment are separate.
- Balance belongs to Enrollment.
- Classroom access is modeled through ClassroomMembership.
- QR codes use classroom-contextual STUDENT, QUICK, and ACTION commands.
- QR image files are generated on demand and are not stored as database blobs.
- The financial ledger is append-oriented and historical.
- Current Enrollment balance is stored for performance.
- Reversals are opposite transactions, not deletion.
- Reversal transactions can themselves be reversed.
- Server-side idempotency is mandatory.
- Weekly allowance and job wages are individually idempotent.
- Reward inventory is optional but strictly enforced when enabled.
- Reward financial reversal and inventory restoration are separate concepts.
- V1 uses service-layer tenant authorization rather than PostgreSQL RLS.
- Archived/historical records are preserved rather than destructively deleted.

# 3. Identifier Strategy

## 3.1 Internal primary keys

Use UUID primary keys for domain entities.

Recommended default: UUIDv7 generated by the application layer.

Reasons:

- stable immutable identity
- good index locality compared with fully random UUIDs
- safe to expose in URLs without relying on sequence obscurity
- easy creation before insert
- no dependency on teacher-facing codes

UUID authorization is never treated as a security boundary. Every request still requires classroom membership authorization.

UUIDv4 is an acceptable fallback if the chosen Python UUIDv7 library is not sufficiently stable at implementation time.

## 3.2 Human-readable classroom codes

Teacher-facing IDs remain text fields scoped to a classroom:

- Enrollment.student_code: 01
- Action.action_code: A01
- QuickAction.quick_action_code: QA1
- BehaviorReason.reason_code: BR1
- Job.job_code: J01
- Reward.reward_code: R01

Codes should be canonical uppercase where letters are allowed and should use a conservative format such as letters, digits, underscore, and hyphen.

Recommended maximum: 32 characters.

Database uniqueness is classroom scoped.

## 3.3 Financial display numbers

FinancialTransaction should use:

- UUID primary key for relationships
- BIGINT display_number generated from a PostgreSQL sequence
- UI formatting such as TX000001

The prefix and zero padding belong in presentation logic. The numeric sequence is concurrency-safe and globally unique.

Sequence gaps are acceptable. A rolled-back transaction may consume a sequence number; financial correctness must not depend on contiguous numbering.

# 5. Proposed Tables

Purpose: authenticated account identity.

Important columns:

- id UUID PK
- email text

Constraints:

- UNIQUE(email_normalized)
- email_normalized stored lowercase by application

Deletion:

- do not hard-delete while referenced by financial/audit records
- account disabling is preferred

Purpose: first-class classroom identity.

Important columns:

- id UUID PK
- name text
- school_year text
- archived_at timestamptz nullable
- created_at timestamptz
- updated_at timestamptz

Hard deletion is not normal once domain history exists.

## 5.5 classroom_memberships

Purpose: user authorization relationship to classroom.

Important columns:

- id UUID PK
- classroom_id UUID FK classrooms
- user_id UUID FK users
- role text: owner, teacher, assistant, school_admin
- joined_at timestamptz
- ended_at timestamptz nullable
- created_by_user_id UUID nullable FK users

Constraints:

- partial UNIQUE(classroom_id, user_id) WHERE ended_at IS NULL
- partial UNIQUE(classroom_id) WHERE role = owner AND ended_at IS NULL

The second constraint guarantees at most one active owner. Application service logic guarantees at least one owner for active classrooms.

Ownership transfer occurs in one database transaction.

Purpose: durable student identity separate from classroom enrollment.

## 5.15 financial_requests

Purpose: idempotency and deterministic replay for logical financial requests.

Important columns:

- id UUID PK
- classroom_id UUID
- idempotency_key text
- request_kind text
- request_fingerprint bytea
- status text: completed, rejected
- rejection_code text nullable
- response_json jsonb nullable
- actor_user_id UUID nullable
- created_at timestamptz
- completed_at timestamptz

Constraints:

- UNIQUE(classroom_id, idempotency_key)
- UNIQUE(id, classroom_id)

Normal flow:

1. begin transaction
2. insert FinancialRequest
3. duplicate key waits for concurrent request outcome or resolves to an existing committed request
4. validate request fingerprint
5. perform business operation
6. on success insert FinancialTransaction and mark completed
7. on expected business rejection mark rejected and commit without a ledger row
8. on technical/database failure roll back the entire transaction, including the FinancialRequest insert

This avoids stranded in-progress rows after process crashes.

- quick_action_id UUID nullable
- job_assignment_id UUID nullable

# 6. Financial Ledger Design

The ledger contains only successfully posted balance changes.

A financial operation conceptually performs:

1. authorize classroom membership
2. begin PostgreSQL transaction
3. create/resolve FinancialRequest idempotency record
4. lock Enrollment FOR UPDATE
5. read authoritative current_balance and ClassroomSettings
6. lock any additional mutable shared resource when needed
7. validate operation
8. calculate balance_after
9. insert FinancialTransaction
10. update Enrollment.current_balance
11. write related domain record, such as RewardPurchase or ScheduledPayment
12. mark FinancialRequest completed
13. commit

Expected business rejection, such as insufficient funds, commits a rejected FinancialRequest but creates no ledger row and changes no balance.

Technical failure rolls everything back.

The CHECK balance_after = balance_before + amount protects ledger arithmetic independently of application code.

# 7. Reversal Design

FinancialTransaction.reverses_transaction_id points to the transaction being reversed.

Rules:

- reversal is a new FinancialTransaction
- amount must equal negative target amount
- reversal uses the same Enrollment and Classroom
- each transaction can be directly reversed at most once
- a reversal may itself be reversed
- original rows never change

Example:

    T1  +10
    R1  -10  reverses T1
    R2  +10  reverses R1
    R3  -10  reverses R2

The partial unique constraint on reverses_transaction_id prevents branching such as two independent reversals of T1.

A classroom/enrollment composite FK ensures a reversal cannot point across accounts.

The opposite-amount rule should be enforced by the financial service and, preferably, by a PostgreSQL constraint trigger during migration implementation because a normal CHECK cannot inspect another row.

Ledger immutability plus an immediate self-FK and CHECK(id <> reverses_transaction_id) prevents normal reversal cycles.

# 8. Idempotency Design

FinancialRequest is the general request-idempotency mechanism.

Recommended client keys are high-entropy UUID-like values.

Uniqueness scope:

    classroom_id + idempotency_key

Request fingerprint is a stable hash of business-significant inputs. If a caller reuses the same idempotency key with a different payload, the server rejects the reuse rather than replaying an unrelated result.

Expected statuses:

- completed
- rejected

There is no durable processing status required because the request row and business mutation live in one PostgreSQL transaction. Until commit, competing inserts on the unique key wait. A crash rolls the uncommitted row back.

Scheduled financial operations additionally use ScheduledPayment logical uniqueness. This is deliberate defense in depth because scheduled payments have stable business identifiers independent of HTTP request retries.

# 9. Authentication / Sessions / Verification Data

Authentication tables are isolated from classroom domain tables.

Password reset and email verification use hashed one-time tokens with expiration and consumed timestamps.

Email verification is represented by users.email_verified_at.

Teacher verification is separate:

- teacher_verification_status
- teacher_verified_at

A future teacher_verification_events or teacher_verification_cases table can be added without changing account identity.

Server sessions use opaque random cookies. Only a hash of the session secret is stored.

Session revocation does not modify classroom history.

---

# 10. Classroom Membership / Roles

ClassroomMembership is the authorization anchor.

Every classroom request should start from:

    authenticated user
      -> active ClassroomMembership
      -> requested Classroom

V1 may expose only owner, but the data model already supports teacher, assistant, and school_admin.

One user has at most one active membership per classroom. The `owner` role includes normal teacher permissions, so an owner does not need a duplicate `teacher` membership row.

Role semantics belong in service authorization policies, not scattered route conditionals.

At most one active owner is enforced in PostgreSQL. The service ensures an active classroom is not left ownerless.

---

# 11. Student / Enrollment Model

Student represents a durable person/alias identity.

Enrollment represents that Student in one Classroom and owns:

- student_code used by STUDENT QR commands
- current balance
- active/end state
- classroom-specific notes

This cleanly supports:

- one Student in multiple classrooms
- separate balances
- transfers
- archived school years
- future account linking

School-year rollover should create a new Classroom and new Enrollment rows. Old Enrollment balances and ledger history remain untouched.

V1 should not globally search or deduplicate Student identities across unrelated teachers.

# 12. Actions / Quick Actions / QR Resolution

QR resolution uses indexed classroom-scoped codes.

STUDENT:01:

    active classroom_id + enrollment.student_code = 01

QUICK:QA1:

    active classroom_id + quick_action.quick_action_code = QA1
    -> assigned Action by immutable action_id

ACTION:A01:

    active classroom_id + action.action_code = A01

Recommended rule: normalize letter-containing codes to uppercase before storage and lookup.

Old printed QR behavior after a code change:

- old code stops resolving
- new generated QR uses new code
- internal UUID and history remain stable
- administrative audit records the code change

No QR image or opaque token table is needed.

---

# 13. Behavior Model

BehaviorEvent is separate from FinancialTransaction because behavior detail may be attached after the financial scan commits.

For a behavior Action with nonzero amount:

- financial transaction posts immediately
- BehaviorEvent is created and linked to it
- reason may initially be null
- teacher can attach reason later

For a zero-point behavior Action:

- BehaviorEvent can exist without a FinancialTransaction

This avoids fake zero-dollar ledger entries while preserving behavioral analytics.

Historical behavior reason name/code is snapshotted into BehaviorEvent when the reason is attached. Later renaming the BehaviorReason does not rewrite the event.

---

# 14. Jobs / Job Assignments / Payroll

Job is the classroom definition.

JobAssignment is historical assignment state.

A partial unique index prevents two simultaneously active copies of the same job assignment for one Enrollment.

Weekly payroll operates per active JobAssignment.

The wage transaction snapshots:

- job code
- job name
- wage

Changing the Job weekly wage later affects future payments only.

---

# 15. Rewards / Purchases / Inventory / Fulfillment

Reward stores the mutable offer and current inventory.

RewardPurchase stores the purchase snapshot and current fulfillment state.

FinancialTransaction stores the point deduction.

RewardFulfillmentEvent preserves redemption history.

RewardInventoryEvent preserves physical stock history.

Purchase transaction:

1. create/resolve FinancialRequest
2. lock Enrollment
3. lock Reward
4. validate reward active/availability/price
5. validate points
6. validate quantity if tracked
7. decrement Reward.quantity_available if tracked
8. insert inventory decrement event if tracked
9. insert FinancialTransaction
10. update Enrollment.current_balance
11. insert RewardPurchase
12. commit

Two concurrent purchases of the final item serialize on the Reward row. Only one can observe quantity 1 and decrement to 0.

Refund/reversal:

- financial reversal always uses normal reversal logic
- teacher separately chooses whether stock is restored
- if restoration is selected, Reward is locked and a RewardInventoryEvent is created in the same transaction as the reversal
- reversal-of-reversal may separately choose an inventory effect and receives its own inventory event

Fulfillment state does not control financial truth.

---

# 16. Automation / Scheduled Payment Idempotency

AutomationRun records an invocation attempt.

ScheduledPayment protects each logical payment.

Allowance uniqueness:

    enrollment_id + period_key

Job wage uniqueness:

    job_assignment_id + period_key

Example period key:

    2026-W43

The exact period-key formatting must be deterministic and timezone-aware.

A job run that crashes after paying 12 of 30 assignments can be run again. The first 12 conflict with existing ScheduledPayment rows and are skipped/replayed; the remaining 18 continue.

AutomationRun status can be partial or failed without risking duplicate money.

# 17. Audit Logging

Three histories remain separate.

## Financial ledger

Permanent point changes only.

## Administrative audit

Configuration and domain changes such as code edits, price changes, role changes, deactivation, inventory corrections, and reason changes.

## Technical logs

Request traces, exceptions, worker output, scheduler output, performance information, and deployment/system diagnostics belong in structured application logs/journald or a later logging service.

Do not put routine technical logs in PostgreSQL business tables.

# 18. Historical Snapshot Strategy

Snapshot values when later mutation would change the historical meaning.

FinancialTransaction snapshots:

- student_code
- Action code/name/kind
- Quick Action code
- Job code/name/wage
- Reward code/name/price

RewardPurchase snapshots:

- reward code/name/type/price

BehaviorEvent snapshots:

- action code/name when applicable
- behavior reason code/name when attached

Do not snapshot every Classroom or Student attribute into every transaction. Classroom and Enrollment records are preserved, so immutable UUID relationships remain valid.

Classroom name and school-year changes are administratively audited rather than duplicated in each ledger row.

# 19. Constraints

Important PostgreSQL constraints include:

- users email_normalized unique
- one active membership per user/classroom
- at most one active owner per classroom
- unique Student code per classroom
- one Student enrollment per classroom
- unique Action code per classroom
- unique Quick Action code per classroom
- Quick Action Action must belong to same classroom
- unique Behavior Reason code per classroom
- behavior reason type must match BehaviorEvent type through composite FK
- unique Job code per classroom
- no duplicate active JobAssignment
- transaction balance_after = balance_before + amount
- no zero-value FinancialTransaction
- one ledger transaction per FinancialRequest
- one direct reversal per transaction
- no self reversal
- Reward quantity never negative
- Reward inventory quantity null when tracking disabled
- one purchase per purchase transaction
- one inventory event per linked financial transaction
- one allowance payment per Enrollment/period
- one job wage per JobAssignment/period
- composite classroom foreign keys prevent cross-classroom domain linkage

Some business rules remain service-level because they depend on mutable settings, such as negative-balance policy.

# 21. Transaction and Locking Strategy

Use a consistent lock order.

## Normal manual or Action transaction

1. FinancialRequest uniqueness
2. Enrollment FOR UPDATE
3. validate
4. ledger + balance

## Reward purchase

1. FinancialRequest uniqueness
2. Enrollment FOR UPDATE
3. Reward FOR UPDATE
4. validate
5. inventory event/purchase/ledger/balance

## Reward reversal with stock change

1. FinancialRequest uniqueness
2. Enrollment FOR UPDATE
3. Reward FOR UPDATE
4. validate reversal
5. ledger/balance
6. inventory event

## Weekly allowance

1. insert ScheduledPayment logical claim
2. FinancialRequest
3. Enrollment FOR UPDATE
4. ledger/balance
5. attach ScheduledPayment transaction

## Weekly job wage

1. validate active JobAssignment
2. insert ScheduledPayment logical claim
3. FinancialRequest
4. Enrollment FOR UPDATE
5. ledger/balance
6. attach ScheduledPayment transaction

## Balance adjustment

1. FinancialRequest
2. Enrollment FOR UPDATE
3. compute desired - current
4. reject no-op or post adjustment
5. ledger/balance

When bulk operations affect many enrollments in one database transaction, lock enrollments in deterministic UUID order. Prefer smaller per-enrollment transactions for large bulk jobs so one blocked student does not hold locks across the entire class unnecessarily.

# 22. Multi-Tenant Isolation

V1 uses service-layer authorization, but the schema should still make tenant mistakes harder.

Classroom-owned tables store classroom_id directly.

Where a child references another classroom-owned row, use a composite FK containing classroom_id.

Examples:

    financial_transactions(enrollment_id, classroom_id)
      -> enrollments(id, classroom_id)

    quick_actions(action_id, classroom_id)
      -> actions(id, classroom_id)

    job_assignments(job_id, classroom_id)
      -> jobs(id, classroom_id)

This prevents cross-classroom relational corruption even if application code passes mismatched UUIDs.

Every service entry point must still prove an active ClassroomMembership for the authenticated user before reading or writing classroom data.

PostgreSQL RLS can be evaluated later as additional defense.

# 24. Integrity Audit Support

The schema supports periodic integrity checks.

## Balance integrity

For each Enrollment:

    opening/current historical total = SUM(FinancialTransaction.amount)

Compare with Enrollment.current_balance.

If the approved design uses an opening-balance transaction, the sum is the full expected balance.

## Reversal integrity

Verify:

- reversal amount = negative target amount
- same Enrollment/Classroom
- no transaction is directly reversed twice
- reversal targets exist

## Scheduled payment integrity

Unique indexes prevent duplicate logical payments.

Audit can verify each ScheduledPayment links to exactly one matching FinancialTransaction.

## Job integrity

Partial unique index prevents duplicate active assignment.

Audit can flag payments after assignment end date or before start date.

## Inventory integrity

Check:

- Reward.quantity_available >= 0
- event arithmetic before + delta = after
- latest event quantity equals Reward.quantity_available
- purchase decrement exists when tracked
- refund restore matches teacher-selected inventory action

## Orphan integrity

Foreign keys prevent most orphaned domain records.

# 25. Important Query Walkthroughs

## 25.1 Resolve STUDENT:01

Authorize active ClassroomMembership, then find active Enrollment by:

    classroom_id = active classroom
    student_code = 01
    active = true

## 25.2 Resolve QUICK:QA1

Find active QuickAction by classroom + QA1, join its assigned active Action, then invoke the normal Action processing path.

## 25.3 Resolve ACTION:A01

Find active Action by classroom + A01 and invoke it directly.

## 25.4 Current balance

Read Enrollment.current_balance after classroom authorization.

## 25.5 Student transaction history

Query FinancialTransaction by enrollment_id ordered by occurred_at/display_number descending.

## 25.6 Expected balance

SUM(amount) across the Enrollment ledger, assuming opening balance is posted as a ledger transaction.

## 25.7 Weekly allowance retry

Insert ScheduledPayment with allowance logical key. Existing unique row means already processed. New row proceeds through central financial posting.

## 25.8 Multiple job wages

Each JobAssignment receives an independent ScheduledPayment and FinancialTransaction, so three active jobs create three wage rows.

## 25.9 Buy last inventory item

Lock Enrollment then Reward. First transaction changes quantity 1 to 0 and commits. Second transaction then observes 0 and rejects without financial deduction.

## 25.10 Reverse transaction

Lock Enrollment, validate unreversed target, post exact opposite FinancialTransaction with reverses_transaction_id.

## 25.11 Reverse a reversal

The target is simply the prior reversal row. Post its exact opposite and point reverses_transaction_id to that reversal.

## 25.12 Behavior analytics

Query BehaviorEvent by classroom/enrollment/date and group by behavior_type/reason. Financial joins are optional.

## 25.13 Archive classroom

Set classrooms.archived_at. Do not delete Enrollment, ledger, jobs, behavior, rewards, or purchase history.

## 25.14 Block Teacher A from Classroom B

Every service query first requires an active ClassroomMembership for authenticated user + classroom. Composite classroom foreign keys then ensure child records cannot cross-link to Classroom B while pretending to belong to Classroom A.

# 26. Risks and Tradeoffs

## Stored balance vs ledger

Risk: current_balance drifts from ledger.

Mitigation: one write service, same DB transaction, DB arithmetic checks, integrity audit.

## Snapshot duplication

Risk: wide ledger table.

Mitigation: snapshot only fields required to preserve historical meaning.

## Composite foreign keys

Risk: more verbose migrations and ORM mappings.

Mitigation: the tenant-consistency protection is worth the added schema clarity.

## Reversal chains

Risk: application code incorrectly treats is_reversed as a simple boolean.

Mitigation: no authoritative reversed flag; use the one-to-one reversal chain and dedicated reversal service.

## Idempotency retention

Risk: FinancialRequest grows indefinitely.

Mitigation: retain financial idempotency records for an intentionally long period; they are small. Do not purge scheduled payment uniqueness while related financial history exists.

## Student identity ambiguity

Risk: accidental sharing/deduplication across unrelated teachers.

Mitigation: no global directory, access through authorized Enrollments, explicit future account-linking model.

## Reward inventory

Risk: oversell or mismatched stock.

Mitigation: Reward row lock, nonnegative DB constraint, inventory event trail, integrity audit.

## Behavior reason attachment

Risk: mutable behavior detail undermines history.

Mitigation: financial row remains immutable; reason attachment is on BehaviorEvent and changes are administratively audited.

# 27. DATABASE DECISIONS REQUIRING APPROVAL

The following decisions should be approved before migrations are created.

## Decision 1 — Opening balance — APPROVED

**Approved behavior:** The system default classroom starting balance is 0. Teachers may configure a different starting balance in Classroom Settings.

When an Enrollment is created, it begins conceptually at zero. If that classroom's configured starting balance is nonzero, QRBank posts an Opening Balance FinancialTransaction in the same creation workflow to move the Enrollment from 0 to the configured value.

If the configured starting balance is 0, no zero-value financial transaction is created.

This means a classroom can use, for example, a starting balance of 50 or 100 without changing the system-wide default.

Benefit: ledger SUM always reconstructs the complete current balance without requiring a hidden baseline field.

## Decision 2 — Student sharing across unrelated teachers — APPROVED

**Approved behavior:** V1 will not globally deduplicate or deliberately share Student rows across unrelated teacher tenants.

A Student may be reused across classrooms when an authorized user already has legitimate access to that Student through their classrooms, but there will be no global student lookup or automatic cross-teacher matching.

If a future student account represents the same person across independently created Student rows, an account-linking layer can connect those identities without rewriting historical Enrollment or ledger data.

Benefit: substantially safer privacy and tenant boundaries.

## Decision 3 — Editing human-readable QR IDs — APPROVED

**Approved behavior:** Authorized teachers may change StudentID, ActionID, QuickActionID, JobID, RewardID, and similar classroom-facing codes.

The internal UUID never changes. The change is written to AdminAuditEvent and historical transactions preserve snapshots.

For scan-enabled codes, the UI must warn that previously printed QR codes using the old code will stop working and should be reprinted.

Benefit: teachers can correct naming or numbering mistakes without corrupting history.

## Decision 4 — Reward fulfillment history — APPROVED

**Approved behavior:** Store both RewardPurchase.fulfillment_status for fast current-state reads and append-only RewardFulfillmentEvent rows for fulfillment/redemption history.

Fulfillment changes do not create financial transactions unless there is a separate financial action such as a purchase reversal/refund.

Benefit: privileges such as Homework Pass can show when they were redeemed or changed, while the store UI remains simple and fast.

---

All four database decisions are approved. The schema is sufficiently defined to proceed to migration planning. Production migrations must still be proposed and reviewed before execution.
