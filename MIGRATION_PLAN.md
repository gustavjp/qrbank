# QRBank Migration Plan

**Status:** Migration Planning Draft  
**Scope:** Ordered Alembic/PostgreSQL migration strategy only  
**Implementation status:** No Alembic revision files or production database changes have been created.

---

# 1. Purpose

This document translates the approved QRBank database design into an implementation order for future Alembic migrations.

It does not authorize schema execution.

The goals are to:

- create tables in dependency-safe order
- make tenant-safe composite foreign keys valid in PostgreSQL
- apply financial constraints before application code depends on them
- avoid circular migration dependencies
- keep destructive rollback risk explicit
- make the initial schema reproducible on an empty PostgreSQL database
- support automated upgrade/constraint tests before deployment

The authoritative inputs remain:

1. `SPEC.md`
2. `ARCHITECTURE.md`
3. `DATABASE_DESIGN.md`

---

# 2. Migration Philosophy

The first QRBank schema should not be emitted as one enormous opaque migration.

Use a small sequence of coherent revisions with explicit dependencies.

Each revision must:

- have one clear domain purpose
- use named constraints and indexes
- contain a valid `upgrade()`
- contain a development-safe `downgrade()` where reasonably possible
- be tested on a fresh PostgreSQL database
- be tested upgrading from the prior revision
- not contain production data
- not silently mutate financial history
- not rely on browser/application validation for database invariants

Initial migrations should favor correctness and clarity over cleverness.

---

# 3. Naming Conventions

Use snake_case PostgreSQL names.

Recommended Alembic/SQLAlchemy naming convention:

- primary key: `pk_<table>`
- foreign key: `fk_<table>__<column(s)>__<reftable>`
- unique constraint: `uq_<table>__<column(s)>`
- check constraint: `ck_<table>__<purpose>`
- regular index: `ix_<table>__<column(s)>`
- partial unique index: `ux_<table>__<purpose>`

Composite names may be shortened if PostgreSQL's identifier-length limit would be exceeded, but the final name must remain understandable.

Avoid auto-generated anonymous constraint names because later migrations need to target constraints reliably.

# 4. Type Strategy

## 4.1 UUIDs

Domain primary keys use PostgreSQL `uuid`.

UUIDv7 values are generated by the application layer.

The database does not need a UUID-generation extension for normal inserts.

Migration tests may explicitly provide UUID values.

## 4.2 Point balances and amounts

Use `integer` for:

- Enrollment.current_balance
- Action.amount
- Job.weekly_wage
- Reward.price_points
- FinancialTransaction.amount
- balance_before
- balance_after
- amount snapshots

Do not use floating point or decimal currency types.

## 4.3 Timestamps

Use `timestamp with time zone` / `timestamptz`.

Database-created timestamps may use `CURRENT_TIMESTAMP` as a server default.

## 4.4 Dates and schedule times

Use:

- `date` for assignment/enrollment start/end dates
- `time without time zone` for classroom-local recurring schedule time
- text IANA timezone name for the classroom timezone

The scheduler combines local day/time with the IANA timezone.

## 4.5 Status/category fields

Recommended V1 approach:

**text columns + named CHECK constraints**, rather than native PostgreSQL ENUM types.

Reasons:

- easier to extend through later Alembic revisions
- fewer PostgreSQL enum lifecycle complications
- values remain strongly constrained
- easier downgrade behavior
- appropriate for a product whose roles/statuses may expand

Examples:

- account_status
- teacher_verification_status
- membership role
- action_kind
- behavior_type
- reward_type
- fulfillment_status
- run_type/status
- financial source/type

Do not leave these as unconstrained free text.

## 4.6 JSON

Use `jsonb` only for intentionally flexible metadata such as:

- FinancialRequest.response_json
- AdminAuditEvent.before_json
- AdminAuditEvent.after_json

Core relational facts must remain typed columns.

# 5. Code and Email Normalization

## 5.1 Email

Store:

- email: teacher-facing original/canonical value
- email_normalized: lowercase normalized lookup value

Create a unique constraint on `email_normalized`.

Do not depend on case-sensitive uniqueness of `email`.

## 5.2 Classroom-facing codes

Student, Action, Quick Action, Job, Behavior Reason, and Reward codes should be normalized by application code before insert/update.

Recommended normalization:

- trim surrounding whitespace
- uppercase letters
- reject empty result

Recommended database CHECK pattern permits a conservative set such as:

    A-Z
    0-9
    underscore
    hyphen

Exact regex should be centralized and used consistently.

Database constraints should reject malformed stored values even if application validation is bypassed.

# 7. Revision 0001 — Identity and Authentication

Create:

- users
- auth_tokens
- user_sessions

## users

Create first because later ownership, actor, and session relationships depend on it.

Important constraints:

- PK(id)
- UNIQUE(email_normalized)
- CHECK(account_status allowed values)
- CHECK(teacher_verification_status allowed values)

Recommended defaults:

- account_status = pending_verification
- teacher_verification_status = not_requested

## auth_tokens

Foreign key:

- user_id -> users.id

Constraints:

- UNIQUE(token_hash)
- CHECK(expires_at > created_at)
- CHECK(token_type allowed values)

Delete behavior:

- deleting a user should not normally occur
- use RESTRICT for domain-protective behavior unless implementation review gives a specific reason for cascading ephemeral auth records

A future account-purge workflow can explicitly remove auth/session rows before permitted user removal.

## user_sessions

Foreign key:

- user_id -> users.id

Constraints:

- UNIQUE(session_token_hash)
- CHECK(expires_at > created_at)

Indexes:

- active/recent sessions by user
- optional expiration index for session cleanup

# 8. Revision 0002 — Classrooms and Memberships

Create:

- classrooms
- classroom_memberships
- classroom_settings

## classrooms

No direct `owner_user_id`.

Fields include:

- UUID id
- name
- school_year
- archived_at
- created_at
- updated_at

## classroom_memberships

Foreign keys:

- classroom_id -> classrooms.id
- user_id -> users.id
- created_by_user_id -> users.id nullable

Create partial unique indexes:

1. one active membership per user/classroom:

    UNIQUE(classroom_id, user_id)
    WHERE ended_at IS NULL

2. at most one active owner:

    UNIQUE(classroom_id)
    WHERE role = 'owner' AND ended_at IS NULL

Use CHECK for allowed roles.

"At least one active owner" remains a service transaction rule because a normal row-level CHECK cannot enforce existence of another row.

## classroom_settings

One-to-one table:

- classroom_id is both PK and FK

Important defaults:

- timezone = America/New_York
- starting_balance = 0
- weekly_allowance_amount = 20
- allow_negative_balance = false
- duplicate_scan_seconds = 0 unless product review later changes it
- sound_enabled = true unless product review later changes it

Schedule day/time defaults should reflect the approved product defaults:

- allowance Monday 06:00 local
- wages Monday 06:10 local

Use CHECK constraints for:

- weekday range
- duplicate scan seconds >= 0
- selection timeout > 0
- valid scheduling values

No classroom-specific Actions/Quick Actions are seeded in this migration. Those are created per classroom by application setup logic later.

---

# 9. Revision 0003 — Students and Enrollments

Create:

- students
- enrollments

## students

Foreign key:

- created_by_user_id -> users.id nullable

Do not enforce global uniqueness on student name or other profile data.

No global deduplication key should be introduced in V1.

## enrollments

Foreign keys:

- classroom_id -> classrooms.id
- student_id -> students.id

Constraints:

- UNIQUE(classroom_id, student_code)
- UNIQUE(classroom_id, student_id)
- UNIQUE(id, classroom_id)
- CHECK(student_code valid normalized format)
- CHECK(ended_on >= started_on when both present)

Default:

- current_balance = 0
- active = true

The database default is zero even when classroom settings specify a nonzero starting balance.

A nonzero classroom starting balance is later posted by the financial service as an Opening Balance FinancialTransaction. It is not written directly into current_balance by a migration/default.

Indexes:

- classroom active student list
- student_id lookup

---

# 10. Revision 0004 — Classroom Definitions

Create definition/configuration tables that financial rows may later reference:

- actions
- quick_actions
- behavior_reasons
- jobs
- job_assignments
- rewards

Create them before the financial ledger because FinancialTransaction can reference Action, Quick Action, Job Assignment, and Reward.

## actions

Constraints:

- UNIQUE(classroom_id, action_code)
- UNIQUE(id, classroom_id)
- action code format
- CHECK(action_kind allowed values)

Composite FK prerequisite:

`UNIQUE(id, classroom_id)` is intentionally redundant with UUID PK uniqueness because PostgreSQL requires a matching unique key for a composite referenced key.

## quick_actions

Constraints:

- UNIQUE(classroom_id, quick_action_code)
- UNIQUE(id, classroom_id)
- CHECK(display_order >= 0)

Composite FK:

    (action_id, classroom_id)
        -> actions(id, classroom_id)

This prevents a Quick Action in one classroom from pointing to an Action in another.

## behavior_reasons

Constraints:

- UNIQUE(classroom_id, reason_code)
- UNIQUE(id, classroom_id)
- UNIQUE(id, classroom_id, behavior_type)
- CHECK(behavior_type in positive/negative)

The triple unique key supports later type-safe BehaviorEvent linking.

## jobs

Constraints:

- UNIQUE(classroom_id, job_code)
- UNIQUE(id, classroom_id)
- CHECK(weekly_wage >= 0)

## job_assignments

Constraints:

- UNIQUE(id, classroom_id)
- composite Enrollment FK
- composite Job FK
- CHECK(ended_on >= started_on)
- partial unique active assignment:

    UNIQUE(enrollment_id, job_id)
    WHERE ended_on IS NULL

The newly clarified `UNIQUE(id, classroom_id)` is required because financial/scheduled rows may use classroom-safe composite references to JobAssignment.

## rewards

Constraints:

- UNIQUE(classroom_id, reward_code)
- UNIQUE(id, classroom_id)
- CHECK(price_points > 0)
- reward type allowed values
- inventory consistency checks
- availability date ordering check

Inventory check should enforce:

    inventory_tracking = true
      => quantity_available IS NOT NULL AND quantity_available >= 0

    inventory_tracking = false
      => quantity_available IS NULL

No reward image binary data is stored in PostgreSQL.

# 11. Revision 0005 — Financial Core

Create:

- financial_requests
- financial_batches
- financial_transactions
- financial transaction display sequence

This is the most critical initial migration.

## 11.1 Display sequence

Create a PostgreSQL BIGINT sequence dedicated to FinancialTransaction.display_number.

Set `display_number` default to `nextval(...)`.

Keep UUID as the PK.

Gaps are valid.

## 11.2 financial_requests

Constraints:

- UNIQUE(classroom_id, idempotency_key)
- UNIQUE(id, classroom_id)
- allowed request status values
- allowed/requested request kind values if the design chooses a closed V1 list

Foreign keys:

- classroom_id -> classrooms
- actor_user_id -> users nullable

The request record participates in the same transaction as financial posting.

## 11.3 financial_batches

Foreign keys:

- classroom_id -> classrooms
- actor_user_id -> users nullable

No balance is stored here.

## 11.4 financial_transactions

Create after all referenced definition tables.

Core constraints:

- UUID PK
- display_number UNIQUE
- financial_request_id UNIQUE
- amount <> 0
- balance_after = balance_before + amount
- CHECK(id <> reverses_transaction_id)
- partial UNIQUE(reverses_transaction_id) WHERE not null
- UNIQUE(id, classroom_id, enrollment_id)

Composite tenant-safe foreign keys:

- (enrollment_id, classroom_id)
    -> enrollments(id, classroom_id)
- (financial_request_id, classroom_id)
    -> financial_requests(id, classroom_id)
- (action_id, classroom_id)
    -> actions(id, classroom_id)
- (quick_action_id, classroom_id)
    -> quick_actions(id, classroom_id)
- (job_assignment_id, classroom_id)
    -> job_assignments(id, classroom_id)
- (reward_id, classroom_id)
    -> rewards(id, classroom_id)

Reversal self-reference should be exact:

    (reverses_transaction_id, classroom_id, enrollment_id)
        -> financial_transactions(id, classroom_id, enrollment_id)

This enforces same classroom and same Enrollment at the database relationship level.

The database cannot express "amount equals exact negative of target amount" with an ordinary CHECK. That will be added in the financial-hardening revision using a constraint trigger after the table exists.

Indexes:

- Enrollment history by occurred_at/display_number
- classroom history by occurred_at/display_number
- reversal lookup
- Action history when Action is present

Deletion policy:

- all financial-domain FKs should use RESTRICT/NO ACTION rather than cascade deletion
- ledger rows are not cascade-deleted

# 12. Revision 0006 — Behavior History

Create:

- behavior_events

Foreign keys:

- composite (enrollment_id, classroom_id)
- behavior_reason composite key including behavior_type
- Action composite classroom key
- financial transaction composite account key when present
- actor/reason-attacher User FKs where applicable

Constraints:

- behavior_type allowed values
- partial UNIQUE(financial_transaction_id) WHERE not null

If the reason is null, reason snapshot fields may also be null.

Reason attachment/update is later handled in application service code plus AdminAuditEvent.

No zero-value financial transaction is required for behavior-only events.

---

# 13. Revision 0007 — Reward Purchases and Inventory History

Create:

- reward_purchases
- reward_fulfillment_events
- reward_inventory_events

## reward_purchases

Create:

- UNIQUE(id, classroom_id), supporting composite tenant FKs
- UNIQUE(purchase_transaction_id)

Composite foreign keys:

- Enrollment + classroom
- Reward + classroom
- purchase FinancialTransaction + classroom + Enrollment

This ensures the financial purchase belongs to the same account as the RewardPurchase.

CHECK fulfillment status allowed values.

## reward_fulfillment_events

Foreign keys:

- reward_purchase_id -> reward_purchases
- actor_user_id -> users nullable

CHECK from/to statuses where present.

Do not cascade-delete fulfillment history.

## reward_inventory_events

Composite foreign keys:

- Reward + classroom
- RewardPurchase + classroom when purchase present
- FinancialTransaction + classroom where relevant

Constraints:

- quantity_before >= 0
- quantity_after >= 0
- quantity_after = quantity_before + delta
- delta <> 0
- partial UNIQUE(financial_transaction_id) where not null if one stock mutation per financial reversal/purchase is the approved service behavior

This table records stock history; Reward.quantity_available remains the current locked value.

# 14. Revision 0008 — Automation and Scheduled Payments

Create:

- automation_runs
- scheduled_payments

## automation_runs

Constraints:

- UNIQUE(id, classroom_id)
- run type/status CHECK constraints
- nonnegative counters

Multiple run attempts for the same period are intentionally allowed.

## scheduled_payments

Foreign keys:

- Enrollment + classroom
- JobAssignment + classroom when job wage
- AutomationRun + classroom when attached
- FinancialTransaction + classroom + Enrollment

Checks:

For allowance:

- payment_type = allowance
- job_assignment_id IS NULL

For job wage:

- payment_type = job_wage
- job_assignment_id IS NOT NULL

Create partial unique indexes:

Allowance:

    UNIQUE(enrollment_id, period_key)
    WHERE payment_type = 'allowance'

Job wage:

    UNIQUE(job_assignment_id, period_key)
    WHERE payment_type = 'job_wage'

These are the authoritative duplicate-payment guards.

AutomationRun is observability only.

# 15. Revision 0009 — Administrative Audit

Create:

- admin_audit_events

Foreign keys:

- classroom_id -> classrooms nullable
- actor_user_id -> users nullable

Fields:

- event_type
- target_type
- target_id
- before_json
- after_json
- request_id
- occurred_at

Indexes:

- classroom + occurred_at
- target_type + target_id + occurred_at

This table is append-oriented.

# 16. Revision 0010 — Financial Hardening

This revision adds correctness mechanisms that are easier to install after all referenced tables exist.

## 16.1 Reversal constraint trigger

Add a PostgreSQL constraint trigger/function that validates, on reversal insert:

- target transaction exists
- same Classroom
- same Enrollment
- reversal amount = negative target amount

The composite self-FK already handles existence/same account; the trigger enforces opposite amount.

Because FinancialTransaction is append-only, the trigger only needs to validate insert behavior.

## 16.2 Ledger immutability

Recommended database hardening:

- normal application role receives SELECT and INSERT on financial_transactions
- normal application role does not receive ordinary UPDATE or DELETE privileges on financial_transactions

If one database role is used for both Alembic and runtime initially, privilege separation may be introduced at deployment hardening time rather than blocking local development.

Do not implement a trigger that prevents Alembic/admin maintenance unless its operational consequences are understood.

## 16.3 Optional audit/integrity views

Do not create materialized financial truth.

Plain diagnostic views may be added later for:

- ledger sum vs stored Enrollment balance
- latest RewardInventoryEvent vs Reward quantity
- scheduled payment linkage

These are optional and not required for the first migration sequence.

---

# 17. Foreign-Key Delete Policy

Default approach for historical/domain tables:

**RESTRICT / NO ACTION**

Do not use broad `ON DELETE CASCADE` through financial history.

Examples that should be protected:

- Classroom with transactions
- Enrollment with transactions
- Action referenced by transactions
- JobAssignment referenced by wages
- Reward referenced by purchases
- FinancialTransaction referenced by reversal/purchase/payment

Ephemeral authentication records may eventually use cascade from User only if account deletion semantics are formally designed.

Until then, prefer explicit cleanup and restrictive relationships.

---

# 18. Defaults vs Application-Created Data

Migrations create schema and safe scalar defaults.

Migrations should **not** create classroom-scoped product data such as:

- QA1–QA10 rows
- A01–Axx rows
- rewards
- jobs
- students
- demo teachers
- production classrooms

When a new classroom is created, application/domain setup code may create default Actions and Quick Action mappings in one controlled transaction.

This prevents migration logic from confusing schema evolution with tenant data provisioning.

---

# 19. Default Classroom Settings

The schema should support the current product defaults.

Recommended initial database defaults:

- starting_balance = 0
- weekly_allowance_amount = 20
- allowance schedule = Monday 06:00 classroom local time
- wage schedule = Monday 06:10 classroom local time
- timezone = America/New_York
- allow_negative_balance = false

Whether allowance/wages are enabled by default should be explicitly set by classroom-creation service logic rather than inferred accidentally.

The migration should not retroactively create financial payments.

# 20. Constraint Ordering

Within each revision:

1. create referenced parent tables
2. create base unique constraints required by composite FKs
3. create child tables
4. add composite FKs
5. add CHECK constraints
6. add partial unique indexes
7. add performance indexes

For PostgreSQL composite FKs, create the exact referenced unique constraint first.

Examples:

Before:

    job_assignments(id, classroom_id)

can be referenced, create:

    UNIQUE(id, classroom_id)

Before:

    financial_transactions(id, classroom_id, enrollment_id)

can be used for reversal/reward/payment relationships, create:

    UNIQUE(id, classroom_id, enrollment_id)

---

# 21. Transactional DDL

PostgreSQL supports transactional DDL for these ordinary schema operations.

Each migration revision should normally run in one migration transaction.

Avoid `CREATE INDEX CONCURRENTLY` in the initial empty-database migrations because:

- tables initially contain no production-scale data
- concurrent index creation cannot run inside a normal transaction
- it adds complexity without benefit at project initialization

Later production migrations on large populated tables may use online/concurrent strategies where appropriate.

---

# 22. Rollback Strategy

## Development and test

Each initial Alembic revision should provide a downgrade in strict reverse dependency order.

Dropping a revision must:

- drop child FKs/indexes first
- drop child tables
- drop parent tables only after dependencies are removed
- drop the financial display sequence after financial_transactions

Automated tests should verify upgrade-to-head and full downgrade on an empty disposable database.

## Production

Once real financial history exists, destructive downgrade is not the preferred production rollback strategy.

Production response to a bad schema release should normally be:

1. stop/disable affected application writes if necessary
2. restore the previous application build when schema-compatible
3. create a forward corrective migration
4. use backup restore only when data corruption/destructive DDL requires it

Do not casually execute a downgrade that drops financial tables on a live database.

Backups must be verified before any destructive production migration.

# 23. Migration Verification Tests

Before any migration PR is approved, run against real PostgreSQL.

Required checks:

## Fresh install

- create empty database
- `alembic upgrade head`
- verify all tables/constraints/indexes exist

## Revision-by-revision upgrade

Upgrade one revision at a time to ensure dependency order is valid.

## Development downgrade

- upgrade head
- downgrade base on disposable database
- upgrade head again

## Constraint tests

Attempt and confirm PostgreSQL rejects:

- duplicate normalized email
- duplicate active classroom membership
- second active classroom owner
- duplicate Student code in one classroom
- malformed QR-facing code
- cross-classroom Quick Action -> Action link
- duplicate active JobAssignment
- reward quantity < 0
- tracked reward with null quantity
- untracked reward with non-null quantity
- FinancialTransaction with incorrect balance arithmetic
- self reversal
- duplicate direct reversal
- cross-classroom transaction/enrollment link
- cross-enrollment reversal
- duplicate allowance payment for period
- duplicate job wage for assignment/period

## Positive tests

Confirm PostgreSQL allows:

- same Student code in two different classrooms
- same Action code in two different classrooms
- same Quick Action code in two different classrooms
- reversal of a reversal
- separate wages for two different JobAssignments for the same Enrollment
- zero current Enrollment balance at creation

# 24. Financial Concurrency Tests After Migrations Exist

Migration completion is not proven only by schema creation.

Database integration tests must later prove:

## Concurrent deduction

Start balance 5, negatives disabled, two requests for -5.

Expected:

- one succeeds
- one rejects
- final current_balance = 0
- one new financial ledger row

## Reward last-item race

Reward quantity 1, two concurrent purchases.

Expected:

- one purchase succeeds
- one rejects
- quantity = 0
- only one purchase deduction
- inventory event trail consistent

## Scheduled-payment retry

Attempt same allowance period twice.

Expected:

- only one ScheduledPayment
- only one FinancialTransaction

## Reversal race

Two attempts to reverse the same target.

Expected:

- only one direct reversal can commit

These are application/service integration tests using the database constraints produced by the migrations.

# 25. Alembic Implementation Rules

When migration files are eventually created:

- hand-review every autogenerated diff
- never accept Alembic autogenerate blindly
- explicitly name partial indexes
- explicitly name composite foreign keys
- ensure downgrade order is dependency-safe
- avoid importing application models into old migration logic when it can make historical migrations unstable
- use SQLAlchemy/Alembic primitives where clear
- use targeted PostgreSQL SQL only where Alembic abstractions are awkward, such as constraint triggers
- never place secrets in migrations
- never place production data in migrations

The migration history is permanent project infrastructure and should remain runnable years later.

# 27. Migration Risks

## Risk: overly large initial revision

Mitigation: use domain-focused revisions listed above.

## Risk: composite FK cannot be created

Cause: missing matching unique key on referenced columns.

Mitigation: create every referenced composite unique constraint before child FKs.

## Risk: PostgreSQL native ENUM becomes hard to evolve

Mitigation: use text + named CHECK constraints for V1 status/category fields.

## Risk: migrations accidentally seed tenant data

Mitigation: schema migrations contain no classroom-specific Actions/Quick Actions or user data.

## Risk: downgrade destroys financial history

Mitigation: production uses forward fixes; destructive downgrade is limited to disposable/dev environments unless explicitly approved with backup recovery.

## Risk: app code assumes cascade deletion

Mitigation: domain/history FKs default to RESTRICT/NO ACTION.

## Risk: trigger complexity obscures financial behavior

Mitigation: use only the narrowly necessary reversal invariant trigger; keep normal balance logic in the central financial service and test both layers.

# 28. MIGRATION DECISIONS REQUIRING APPROVAL

Before actual Alembic revision files are generated, the following implementation choices should be approved.

## Decision 1 — Status/category representation — APPROVED

**Approved behavior:** use PostgreSQL text columns with named CHECK constraints rather than native PostgreSQL ENUM types for V1.

This keeps the values constrained but makes future additions such as new roles, reward states, sources, and automation states easier to migrate.

## Decision 2 — Initial migration packaging — APPROVED

**Approved behavior:** use the 10 ordered domain migrations in this document rather than one giant initial migration.

This makes dependency review, debugging, test failures, and future maintenance clearer while still producing the same final schema.

## Decision 3 — Database reversal hardening

**Recommendation:** add a PostgreSQL constraint trigger that enforces reversal amount = exact negative of the target transaction, while the central financial service remains responsible for normal reversal processing.

This gives the most sensitive ledger invariant a database-level backstop without moving the whole financial engine into triggers.

---

After these migration decisions are approved, the next phase may generate the actual Alembic revision files on a separate implementation branch and run them against a disposable PostgreSQL test database before any deployment.
